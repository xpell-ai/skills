# Developer Console

- Identify the backend profile, actual static root and returned XVM view. The normal client builds to `server/work/public`. The sealed RC1 composition serves `candidate-ui` from its release. Trace the rendered controls through the served HTML/JS/CSS, the live `server-xvm.get-view` response, and the active gateway. Stage a view change against the verified feature surface and use the documented reload or separately authorized restart.
- Check Google Identity Services client and browser origin against the selected profile. For existing-owner linking, use the documented password confirmation and verified Google subject flow. Treat linking and signup as distinct. Retain password fallback and verify account continuity. A Google button denial before account selection is an upstream client/origin diagnostic. Confirm the exact request, response and configured origins before another activation.
- Inspect signed role, account scope, operation admission and storage capability independently. The Console email allowlist can expose navigation without elevating the signed role. Transaction Exceptions is read-only in the reviewed Console. Signed owners see their own account, and cross-account reads require the server's qualifying admin scope. Recovery uses a separately authorized operator path.
- Use the selected account's server-confirmed data. Validate the actual SQLite lookup and authorization contract. Show structured Wormholes errors as readable text and gate mutating controls on verified server capability. Test ordinary-user denial and selected-account balance. For Model Catalog operations, verify actual gateway support and use the catalog's transfer runbook.

**Historical lesson.** A stale persisted XVM dashboard appeared with the correct served asset bytes, including with browser cache bypass. Compare both inputs before rebuilding or replacing the Console.
